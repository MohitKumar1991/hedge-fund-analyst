How Analyst Kit analytics work

skills/analyst-kit-core

Every Analyst Kit skill run is logged twice: a local leg that always writes JSONL to the user's own machine, and a remote leg that sends one small, consent-gated event to PostHog. Everything lives in a single ~100-line bash script, skills/analyst-kit-core/bin/analyst-kit-log — there is no SDK, no batching, and exactly one remote event type: skill_run.

When does an event fire?

Every shipped SKILL.md carries generated Preamble / Completion blocks. The agent runs the Preamble at skill start (which logs start locally) and the Completion block at the end (which logs end locally and fires the PostHog event). Note the asymmetry: PostHog only ever sees end and CRASH events — never start.

The PostHog API being used

Endpoint & mechanics

  • API: PostHog's public single-event Capture API — POST {host}/capture/ with a JSON body. No SDK (posthog-node/posthog-js are not used), no /batch/ endpoint, no person-profile $set properties — just one raw event per call.
  • Auth: the project API key travels in the JSON body (api_key field), as the Capture API expects. It's a phc_… public write-only ingest key — it can only create events, never read them — which is why a default is safely hardcoded in the script.
  • Transport: curl -sf --max-time 3 … & — backgrounded, output discarded, hard 3-second cap. A failed send is silently dropped; telemetry can never block or fail a skill (the script's contract is "never exits non-zero").
  • Identity: in community tier a UUID is lazily generated into ~/.analyst-kit/device-id (uuidgen, falling back to /dev/urandom) so usage counts deduplicate per machine. In anonymous tier every event uses distinct_id: "anon", so all anonymous users collapse into one PostHog person.

User identity — two persistent ids, two audiences

There is no account, login, or profile. Two independent machine-local ids exist, they are generated differently, sent to different parties, and never appear together in the same request: PostHog never sees user-id; SEC EDGAR never sees device-id.

How the SEC UA is derived: ensure-identity writes the timestamp to user-id and mirrors SEC_EDGAR_UA="analyst-kit akit<id>@gmail.com" into ~/.analyst-kit/.env. Each SEC skill's vendored edgar.py independently re-derives the same UA from user-id (_default_ua()), honoring an explicit SEC_EDGAR_UA env var first and falling back to a generic shared UA if no id exists yet. The akit…@gmail.com address is synthetic — SEC asks for a contact string but does not verify it.
Privacy shape: neither id is derived from the user — no hostname, username, hardware serial, MAC address, or email is read. device-id is pure randomness; user-id reveals only when the kit was first run (second-level resolution), which also means two installs in the same second would share a UA. Both live in plain text under ~/.analyst-kit/ and are user-inspectable.

Crash detection — the clever bit

log start drops a .pending-<session>-<skill> marker; log end consumes it (and derives duration_s from its timestamp). If a skill run dies before its Completion block — agent crash, killed session — the marker is orphaned. The next log start in any other session sweeps stale markers, finalizes each as an end event with outcome: "CRASH", and fires that to PostHog too. So crash telemetry arrives late, attributed to the crashed skill, with duration_s: 0 and session: "stale" locally.

Things worth knowing (and one doc bug)

Docs contradict the code on the default tier

skills/analyst-kit-core/SKILL.md:48 says "Defaults: telemetry=off", but bin/analyst-kit-config:13 defaults to community (on) — and SKILL.md's own "Telemetry tiers" section (line 97) agrees with the code. Line 48 looks stale and should read telemetry=community.
PostHog never sees start events. Remote analytics are completion-only, so "skills started but never finished (without crashing a marker sweep)" is invisible remotely — a deliberate minimal-data choice.
The tier itself is sent as a property (properties.tier), so the maintainers can segment community vs anonymous volume in PostHog.
Robustness contract: no set -e, every write is || true, the script always exits 0, and the curl is backgrounded with a 3s cap — a total telemetry failure can never break a skill run.
PROPOSAL — deeper AI observability

Goal: answer three questions today's telemetry can't

Today's remote telemetry is one skill_run event per completion. PostHog's AI observability product (docs: posthog.com/docs/ai-observability) adds a purpose-built event model with an LLM analytics dashboard, trace viewer, and automatic cost computation. Here's the gap:

QuestionToday (skill_run)With AI observability
1 · What prompts are used? nothing — no content ever leaves the machine (by design) $ai_generation carries $ai_input (message list) and $ai_output_choices; $ai_trace shows the whole conversation in PostHog's trace viewer
2 · What skills & data are invoked? partial — skill name, outcome, duration; no data sources, and events from one session can't be joined together each skill run becomes an $ai_span inside a session trace ($ai_trace_id); a data_sources property (from the skill's env: frontmatter) records which APIs it can hit; tool usage counts are parsed from the session transcript
3 · Cost & turns per task? nothing — wall-clock duration only one $ai_generation per LLM call with $ai_input_tokens / $ai_output_tokens / cache tokens; PostHog computes USD cost automatically by matching $ai_model+$ai_provider against OpenRouter pricing; turns = generations per trace

PostHog's AI event model in 30 seconds

$ai_trace

One task or session — groups everything below via $ai_trace_id. Aggregated tokens + latency. Multi-conversation grouping via $ai_session_id.

$ai_span

A step inside a trace — a tool execution, retrieval, or (for us) a skill run. Has $ai_span_id, $ai_span_name, $ai_parent_id, duration, input/output, error info.

$ai_generation

One LLM call: $ai_model, $ai_provider, $ai_input, $ai_output_choices, tokens (incl. $ai_cache_read_input_tokens / $ai_cache_creation_input_tokens — Anthropic-aware), $ai_latency, $ai_stop_reason, and cost ($ai_total_cost_usd, auto-derived if omitted).

All are ordinary PostHog events — they flow through the same POST /capture/ API our curl already uses; the $ai_* names are what light up the LLM analytics dashboard. Pricing note: first 100k LLM events/month free, then ~$0.00006/event.

Decision: we own the pipeline

Direction chosen: analyst-kit owns the whole analytics pipeline — no dependency on PostHog's Claude Code plugin — because the kit must observe the agent identically across harnesses (Claude Code plugin, Codex, OpenClaw, Cowork, installer). Hooks are an accuracy upgrade on the plugin channel; the Preamble/Completion markdown blocks are the universal fallback, where the agent itself is the instrumentation.

The intent trick — Q1 on every harness, no extra LLM call

We never summarize the prompt programmatically. The agent that did the task writes the one-line intent_summary itself, as part of the Completion epilogue it already runs (the same instruction-following mechanism that fills in OUTCOME today). Hooks capture but can't summarize; a separate LLM call would need a key, latency, and spend; the agent has the full conversation in context and the marginal cost is ~30 output tokens inside a turn that's already running. Crucially it summarizes the realized task, not the literal prompt — a follow-up like "now do the same for AMD" or "continue" yields "comparative deep dive on AMD — datacenter growth", which no prompt-only summarizer could produce.

  • Quality control: the template shows the format and an example; length capped at 140 chars by analyst-kit-track.
  • Crash case: if the agent died after the epilogue, the stashed intent still ships with the swept task_completed {crashed:true}.

The consent problem — this changes the privacy promise

Prompts are exactly what we promise never to send

The current pledge (SKILL.md, onboarding, this page): remote events never include repo names, paths, tickers, or content. Task intent in a hedge-fund workflow is tickers, theses, and client material — so intent capture cannot ride on the existing community tier. It lives behind two new explicit opt-in tiers (insights: agent-written summary; full: raw prompt), and the defaults stay exactly as they are today.

Risks & mitigations

  • Transcript format drift: the session JSONL is not a stable public API; the parser must be defensive and fail silent — a parse failure sends task_completed with source:"agent" fields only, never nothing.
  • Agent-as-instrumentation is best-effort: on hook-less channels the epilogue depends on the agent actually running it (same trust level as today's skill_run); the source property lets dashboards separate deterministic from agent-reported data.
  • Intent quality drift: agents may write vague summaries; the epilogue template should show a one-line example format ("<action> on <subject> for <goal>") and cap length.
  • Payload size: raw prompts (full tier) are truncated to a fixed cap before the curl; intent_summary capped at ~140 chars.
  • Event volume: ~3–6 events per task (no per-tool events by design) — negligible against PostHog's 100k/month free LLM-event allowance.
  • python3 dependency for the transcript parse — acceptable; several skills already require python, and its absence just downgrades to agent-level fidelity.
  • Privacy promise change: insights/full carry task content (summaries contain tickers). Onboarding + SKILL.md copy must be rewritten and both tiers kept strictly opt-in; community default behavior is unchanged.
